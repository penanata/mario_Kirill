# MVP-план: лёгкая ops-система «Деревья»

## 1. Цель

Единая простая система вместо хаоса YouGile / Telegram / таблиц: актуальный прайс поставщика с историей, заказы с деньгами и календарём, мобильный список дня для поставщика. Архитектура C — своя лёгкая система; приоритет — быстро и просто, без лишнего.

## 2. Scope MVP (фаза 1)

**Входит**
- Прайс: цена поставщика + цена продажи; история изменений
- Заказы: дата, адрес, телефон, состав, наличные / банк
- Календарь заказов (кто / куда / когда)
- Мобильный день поставщика: что везти, куда, кому, суммы, тип оплаты

**Не входит**
- Автоимпорт из Telegram
- Полный расчёт зарплат / налогов
- Несколько поставщиков
- Пересборка публичного сайта

## 3. Роли и экраны

| Роль | Экраны |
|------|--------|
| **Наталия** | Прайс, создание/правка заказов, календарь, передача дня поставщику |
| **Дарья** | То же (менеджер): прайс, заказы, календарь, связь с поставщиком |
| **Светлана** | Список заказов + суммы (закуп / клиент / маржа по заказу), календарь |
| **Поставщик** | Мобильный день (состав, адрес/клиент, суммы, нал/банк) + **правка цен поставщика** (основной редактор прайса) |

Логин простой (логин/пароль или magic-link). Без сложных ролей-матриц: менеджеры vs поставщик.

## 4. Модель данных (сущности)

- **Product** — название, единица, активен
- **Price** — product_id, supplier_price, sale_price, valid_from, changed_by, note
- **Order** — date, address, phone, client_name?, payment_type (cash|bank), status (draft|confirmed|done|cancel), totals snapshot
- **OrderLine** — product_id, qty, supplier_price_at_order, sale_price_at_order
- **User** — name, role (manager|supplier|finance), phone?

Цены в строке заказа — снимок на момент фиксации; текущий прайс живёт отдельно.

## 5. Правило смены цены поставщика

- **Кто меняет:** цену поставщика **преимущественно правит поставщик** с телефона; менеджеры могут поправить при необходимости. Цену продажи клиенту правят менеджеры.
- Смена `supplier_price` / `sale_price` пишет новую запись в историю; прошлые заказы **не** пересчитываются.
- Подтверждённые и закрытые заказы хранят свои `*_at_order`.
- Открытые черновики (`draft`): при смене цены — флаг «цена изменилась» + пересчёт строк по новому прайсу только после явного подтверждения менеджером (не молча).

## 6. Стек (быстрый скучный MVP)

- **Next.js + SQLite (или Postgres на Railway/Fly) + простой UI** — один деплой, мало движущихся частей
- Auth: Clerk / Auth.js или даже один shared password на старте
- Mobile-first CSS для экрана поставщика (PWA не обязательна в фазе 1)
- Без микросервисов, без Telegram-ботов, без отдельного админ-фреймворка

**Репозиторий** [penanata/mario_Kirill](https://github.com/penanata/mario_Kirill): одностраничная canvas-игра, к ops **не относится** — стартовать с нуля.

## 7. Порядок сборки (срезы ~1 неделя)

1. Каркас: auth, роли, Products + Prices + история цен
2. Заказы + строки со снимком цен + правило draft-флага
3. Календарь по дате доставки
4. Мобильный день поставщика (фильтр по дате)
5. Полировка сумм/маржи для Светланы, импорт ~150 позиций из таблицы, пилот на реальных заказах

## 8. Решения зафиксированы

- Архитектура C, быстрый простой MVP.
- Цену поставщика в системе преимущественно меняет **поставщик**; менеджеры — запасной вариант.
